# External programs and media output

Read this when the package runs an external program, or its output is media or other binary files. A NuGet package that writes files reads this, not [npm-files.md](npm-files.md), whose kit is npm's. Tested on TrailerClipper 2.0.0 and its tool `tclipper` (2026-09-30), which run ffmpeg and ffprobe and write clipped copies.

- **Which program ran.** The output's header names the binary every case runs, its version line (the first line of `ffmpeg -version`) and how the package found it: an option, its environment variable, PATH or a known install folder. Each tool transcript prints the route again. The pages name the builds: ffmpeg 9.0.1 (gyan.dev, from winget) on Windows, n9.0.2 (BtbN) on Linux.
- **Not found.** Make "not found" through the package's own seams: PATH without the program and its variable unset. A seam can be impossible. On Windows TrailerClipper's search includes winget's Packages folder, a known folder found through SHGetKnownFolderPath, not an environment variable, so a run with ffmpeg off PATH still found it. Those cases ran on Linux (PATH `/usr/bin:/bin`, ffmpeg in scratch), and the page says that taking a winget ffmpeg off PATH does not hide it.
- **Heap addresses.** ffmpeg's messages carry an address that changes every run (`[mp3 @ 0x...]`). Mask it with a regular expression (`@ (0x)?[0-9a-f]{8,16}\]` to `@ <address>]`), and say on the page what `<address>` stands for.
- **Version drift.** Windows and Linux ran different ffmpeg builds; label each output with the build, and compare the two runs case by case. An old version can bundle its own program: TrailerClipper 1.1.0 carries a 2015 ffmpeg inside MediaToolkit, so its answers come from that build, not the one on PATH.
- **Fixtures made by the program.** The run made its inputs with ffmpeg's lavfi sources, `testsrc` for video and `sine` for audio, ten seconds each, one per extension the pages show (MP4, MP3, WAV, M4B), beside a Matroska and a text file that show what is skipped. The pages say the inputs came from ffmpeg's test sources.
- **Facts, never bytes.** After each case, list the folder: each file relative with `/`, in ordinal order, with ffprobe's duration to three decimals and its streams (`Episodes/clipped/ep1.mp4: 8.000 s; video h264, audio aac`), a size for a file that is not media, and the text of a JSON file.
- **Durations by codec.** Cutting 2 s off a 10 s file gave 8.000 s for MP4, MP3 and WAV and 8.011 s for M4B (AAC). Show the number as printed, never rounded, with the reason on the page: ffmpeg writes whole audio frames.
- **A fresh copy per case.** As npm-files.md's kit does for npm, the .NET program builds the fixtures once into a source folder and copies each case's input folders into `cases/<case>` before it runs (a `Fresh()` helper), so no case sees another's copies. The library prints absolute output paths, so that folder is masked as `<cwd>` for that case only. The run-wide masks (`<work>`, `<home>`, `<nuget>`, `<temp>`, and `<ffmpeg>` on Linux) stay for every case.
