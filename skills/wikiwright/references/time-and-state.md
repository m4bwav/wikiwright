# Time-dependent output and state that outlives a call

Read this when the output depends on time (an expiry, a lifetime) or on state that outlives a call, such as a cache, a static or a container. Tested on CachingServiceWithAOPSupport 2.0.0 (2026-09-30), whose cached results expire and whose default store is `MemoryCache.Default`.

- **Expiry through what a caller controls.** Show it only with lifetimes the caller sets: the attribute (`[Cache(0, 0, 30)]`, `[Cache(0)]`), a bare `[Cache]` under a `MemoryCacheService(TimeSpan.FromSeconds(1))` registered as the service, and `Set` replacing a value cached by key. The one-second service stood in for the module's five minutes.
- **Margins of at least one second.** A one-second lifetime was checked after 2.5 s; a three-second lifetime was read at 0, 1, 2 and 3.6 s, which showed that expiry is absolute (a sliding lifetime would have lasted until 5 s). Labels such as `after 2.5 s` are text the example prints, not measured times.
- **Two complete runs are the proof.** Run the whole program twice, one after the other, and compare with `WW diffout <first output> <second output>`: nothing may differ (56 of 56 sections on Windows, 47 of 47 on Linux). Say it on the page, before the examples that sleep: "two complete runs printed the same on every runtime and dependency set". Between Windows and Linux, compare config by config: when the config sets differ, `diffout` reports every section whose `on:` line changed.
- **What cannot be shown stably** is described and marked, with the reason: "'Never expires' is not shown by a run, since no run can wait that long". A dependency's own behaviour gets "was not tested" (eviction under memory pressure), and a call that would hang gets "Not shown, since the example would hang" (a pending `Task` as an argument).
- **One process per case when state is process-global.** `MemoryCache.Default` carries entries from one case to the next in one process, across instances and containers, as any static cache or container would. The run compiled each example into one child app per config and ran every example in its own process, so each started with an empty store. The pages then show the sharing on purpose ("One store for the whole process") and a recipe that gives each test a store of its own.
